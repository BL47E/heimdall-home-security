# Service switch to 0.1.0-342daa1 — November 25, 2026

The owner asked why the new release could not control the installed service and requested the fix. Cause: by design, `lib/service.py` lets a release control `heimdall-monitor.service` only when the unit's release path, data directory and owner match the calling release. Inspection showed every installed unit (monitor, cleanup, Discord) and the launcher still referenced the `0.1.0-vt` release, so the new CLI honestly refused to manage a unit belonging to another release.

Backups on blue under `~/heimdall/evidence/2026-11-25-service-switch/` (mode 600): the three service units, the launcher and `state-before.json`. Before the switch the monitor was active on `0.1.0-vt` (PID 1368) with live state at 45 events and zero alerts. The three service units were prepared with only the release path changed to `0.1.0-342daa1`; `systemd-analyze verify` accepted them, and they were installed root-owned mode 644 followed by `daemon-reload`. The launcher wrapper now executes the new release's CLI. A first attempt aborted safely at unit verification without changing anything (prepared files needed proper unit filenames and sudo needs a tty); nothing was modified in that attempt.

`heimdall-monitor.service` restarted at 20:31:59 UTC and came back active with the new release. `~/heimdall/heimdall status` from the new CLI reports the monitor running with available coverage and the manager correctly identified as systemd — the control identity now matches. The cleanup and Discord timers were left to trigger their next runs against the new units without restart. Live state was preserved in the same file with cursor continuity: 59 events and zero alerts after the switch, the increase being real SSH journal activity from this session's own logins during the switching window. No alert or review history was lost.

Limits: unprivileged start/stop remains denied by Ubuntu policy exactly as designed; the restart used an administrator password prompt over an authorized SSH session, supplied through the same private channel as earlier steps and never stored. The dashboard process was not running during this check. No firewall, network, account or provider change accompanied the switch.
