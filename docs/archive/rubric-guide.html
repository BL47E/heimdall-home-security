1. Project in one page

Audience and problem

Heimdall is for a home NAS or home-server owner who wants selected security events from devices in one place, with a plain explanation of what matched and what to review. The user wants useful context without maintaining a full security operations stack.

Proposed flow

StageWhat happensEvidence to show
1. ReceiveA supported NAS or router forwards syslog events to Heimdall over the local network.Source configuration and sample messages.
2. NormalizeHeimdall parses selected fields into a documented internal event shape.Valid and malformed input examples.
3. Detect and groupLocal rules find a small set of patterns, beginning with repeated failed logins, and group related events.Rule ID, matched facts, grouped event references.
4. ExplainThe alert shows its severity, evidence, and a suggested next step.One example at each supported severity.
5. Store and notifyAlerts are kept in SQLite; configured alerts can be sent to an optional notification provider.Restart-persistent record and notification delivery log.
Scope boundary: the first release recommends actions for the owner. It does not block addresses, lock accounts, delete files, or change NAS configuration.

3. Project design — 6 marks

Measurable first-release objectives

  1. Receive and normalize the first documented NAS or router syslog format, with source identity and timestamps visible in every accepted event.
  2. Demonstrate each first-release authentication rule with sample events, and show the matched facts and reason for the resulting severity.
  3. Persist alerts in SQLite across a container restart and demonstrate offline operation with no API key or external service required.

Methodology

  1. Choose one target device and document the events it can forward.
  2. Define the normalized event and alert shapes before implementation.
  3. Receive and validate syslog input; bound message sizes and reject malformed messages safely.
  4. Apply transparent local rules and group duplicate events.
  5. Persist the event and alert, then display the rule, evidence, severity, and recommendation.
  6. Test the same examples offline; add notification and optional enrichment only after local triage works.

Severity guidance

Use a small severity scale and make every level traceable to matched facts. Severity is a project rule, not a universal measure of threat. Missing context should be visible rather than treated as proof of safety.

6. Project report and communication — 12 marks

Report checklist

  • Explain the home user, the event sources, the problem, and the product boundary.
  • Compare existing systems by their documented roles and cite primary documentation.
  • Separate implemented, simulated, and planned behavior throughout the report.
  • Include the event contract, detection rules, severity explanations, test cases, results, limitations, and privacy decisions.
  • Do not claim a measured resource footprint, lower false-positive rate, or time saving without test evidence.

Presentation sequence

  1. Introduce the home NAS user and the problem of scattered security events.
  2. Show existing tools and explain Heimdall's narrower intended role.
  3. Demonstrate event intake, one local rule, the explanation, and stored history.
  4. Show offline mode and explain owner approval for any response.
  5. Close with measured results, current limitations, and the next implementation phase.
Current repository state: the interactive site is a browser simulation. It does not read syslog, call external services, write to SQLite, or send notifications.
